01 · Topology

System map

Four backing systems, each holding a different class of data. The split is deliberate: financial records never leave the user's Drive, and Firestore only carries what two people must both be able to read.

Read it as a data-residency diagram. Financial records sit in the user's Drive; Firestore holds only what a second person must read. The AI providers are reached exclusively through Functions, so no API key ever ships in the client, and the client never talks to Groq or Gemini directly.

02 · Navigation

Screen map

Sixteen routes behind three guards. The left column is the one-way onboarding funnel; the right is the app proper, reachable from the tab bar.

A Circle link opened while signed out parks its code in device storage, sends you through sign-in, and resumes the join automatically — the one place a public route hands off into the guarded app.

03 · The model

Budget model

Everything is a percentage of monthly income. Fifteen categories fall into five groups whose defaults encode 50/30/20, and the allocation must total 100% before it can be saved.

Every entry stores the category limit and the resulting saving at the moment it was created, so changing the budget later never rewrites history. core/models/category-definitions.ts is the single source of truth for names, icons, colours, groups and percentages — nothing else hard-codes a category.

Two categories sit at 0%. Miscellaneous and Debt Payment are Buffer-group categories with no allocation — they must exist so spend can be recorded, but they deliberately do not consume the plan. A category with a zero limit but non-zero spend shows as 100% and "over", which is the intended signal.

05 · The correctness decision

Derived balances

The most consequential design choice in the codebase, and it came from a real production bug.

Before — stored balance

Each account carried a mutable balance that synced as part of the record. Under last-writer-wins merging, two devices editing near-simultaneously each dropped the other's delta.

audited drift: +37,909 (Cash) · +86,056.86 (HDFC)

After — derived balance

The underlying records were add-only with tombstones and had converged perfectly. Only the summary number had not. So the number became a cache recomputed from the records.

drift is now structurally impossible

Credit cards use the same mechanism against an openingOutstanding anchor, back-solved once for cards created before the anchor existed so no false banner appears.

06 · Timeline

Credit card cycle

A card statement is reconstructed backwards from current records, shown as an estimate, then pinned by the user — and five one-shot reminders are recomputed after every change.

Utilisation alerts fire only on an upward crossing of 30% or 80%, so hovering just above a threshold never re-alerts — but paying down and re-approaching does.

07 · Two devices, one ledger

Family sync

Owner and partner share one Drive backup, but never fight over the file. Convergence runs through a Firestore record ledger with four guards that each exist because of a specific bug.

Family mode also merges rather than replaces when reading Drive: expenses merge by timestamp, accounts and debts by updatedAt, audit logs are union-only. A partner's write can never wipe the other side's entries.

08 · Group money

Circle settlement

All arithmetic in integer paise, so every member's device computes byte-identical results. Sorting is what makes the leftover paisa deterministic.

Ties are broken by member id, everywhere. Sorting participants before distributing the leftover paisa, and sorting creditors and debtors by amount with member id as the tie-break, is what guarantees every device produces the same answer without ever coordinating.

09 · Durability

Persistence and races

Ten named defences, each guarding a specific failure. Together they are why an offline write, a crash mid-upload and a simultaneous partner edit all resolve without loss.

The offline rule. All Firestore access must go through getSharedFirestore(). The first initialiser fixes the cache settings for the whole app, so one stray getFirestore() silently downgrades every session to a memory-only cache — and offline family writes are then lost on restart, with no error anywhere.

Transient failure handling

Network errors, 429s and 5xx responses schedule a background flush with exponential backoff from 5 seconds to 5 minutes, and the sync chip reads syncing rather than error. A 401 triggers exactly one silent token refresh and retry. Only 403 and 404 surface as real errors. Drive reads carry no-cache headers and a cache-busting parameter, because a stale CDN copy would look like data loss.

Minimal Google scopes

Only drive.appdata plus openid email profile. Full Drive was dropped in v8 and Spreadsheets in v9; a scope-version bump forces re-consent.

Data residency

Financial records live in the user's own Drive. Firestore holds sync metadata, group splits, subscription status and push tokens — nothing else.

Receipts stay private

Uploaded to the private appDataFolder, invisible in the Drive UI and never shared with a family partner.

SMS never leaves the device

Bank notification text is classified on-device. Only a local dedupe fingerprint is stored, and nothing is sent to any AI endpoint.

13 · Off-app surface

Android

Twenty-five Java classes whose whole purpose is to let the user log money without opening the app.

Quick Expense widget

Resizable with three height tiers. Category buttons plus dedicated More and Credit actions, a native bottom-sheet form with voice capture, and a daily insight showing today's spend against the calculated budget.

on-device category prediction: recency decay + time-of-day + weekday bonus, no network

Daily Streak widget

A day counts when at least one expense is logged. The streak survives until midnight, and a 20:00 reminder fires only if today is still empty.

read-only — no network, no auth, no writes

Notification listener

Reads bank and UPI notifications on-device and runs a deterministic nine-way classifier. Prompts only on high-confidence spends and credits; ignores OTPs, balances, and failed or pending transactions.

everything detected is written to the local inbox before the prompt is posted

WorkManager sync

Drains the widget queue with the app closed: applies effects locally, then either calls the family ledger commit or performs a full Drive round trip using a stored refresh token.

queue items are stamped with the account that captured them
Widgets repaint themselves to match the app. They read the same pf-palette and pf-style values and render their body to a Bitmap on a software canvas, because RemoteViews XML cannot express blur or per-palette gradients. Fifteen storage keys are read by Java — renaming one on the web side without mirroring it in the native constants file silently breaks the widget.

Before you edit anything shared

Touches money?

Update the matching spec in core/utils/ and re-run the unit suite. Every algorithm there has one.

Touches the backup document?

Update the contract spec, the Settings export and the restore parser, plus the native sync worker if Java writes it.

Touches a storage key?

Mirror it in the native constants file and update the key contract spec. Fifteen keys are read by Java.

Touches synced state?

Check the ledger diff and apply utilities, and add the new record type to the ledger union.

Adds a Firestore read or write?

Rules default to deny — add the rule, and an index if you query it.

Adds a Pro feature?

Gate it on the client for UX and on the server for security. One without the other is a hole.
